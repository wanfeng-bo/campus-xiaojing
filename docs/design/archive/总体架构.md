# 总体架构



















## 1. 产品目标与第一阶段终点

平台面向一所中学，采用单校、模块化单体和网页形态，目标不是做一个报修聊天框，而是做一套学校可以直接使用的日常管理系统。

第一阶段的候选模块池为：报修、内务、卫生、纪律、请假、制度资料、通知、值班、校历、场地预约、物资申领、通讯录、班级学生查询、学校地点。

这 14 个模块只是陪跑清单，不是“全部做完才算完成”的交付合同。每完成一个可独立运行、已形成 checkpoint 的模块，必须停止并交用户判断。用户在任一完整 checkpoint 后判断“已经够用、可以给学校使用”，第一阶段即到终点；未完成模块不注册、不宣传、不上线，半成品不能成为终点。

第一阶段交付前不做设备接入和教学功能。第二阶段、第三阶段只在学校已经使用第一阶段后再启动。

## 2. 第一阶段小静内核设计定稿

### 2.1 五条铁律

1. 大模型理解人话是必选项。老师每一句被系统接纳的自然语言都必须经过一次超级大脑理解调用；不得用关键词、正则或条件分支冒充理解，不自动重试。
2. AI 不直接操作数据。超级大脑只返回候选含义和表达候选，不持有数据库写能力、业务 Handler、操作者身份或正式动作凭据。
3. 系统持有的敏感值不进入大模型。老师原话里自己写出的内容属于明确例外；系统不得把同一值从登录会话、数据库、通讯录或模块结果再次注入模型。
4. 正式动作必须由老师点击确认。自然语言中的“确认、提交、同意”只能形成候选，不能直接产生正式影响。
5. 内核定义模块接入格式，模块定义自己的事实、权限、状态和处理规则。模块不适配就修改模块或应用侧适配层；内核不因某个业务的字段、流程或页面而改变。

### 2.2 三方职责

#### 内核：零理解

内核只做：

- 建立和恢复独立对话；
- 顺序收下老师原话并管理一次一个活动回合；
- 按固定格式组装模型安全上下文并调用超级大脑；
- 校验协议外壳，按超级大脑返回的模块句柄整包转发；
- 接收模块结果，按模块声明的呈现档位转发、调用第二次表达或机械填槽；
- 执行会话、回合、模块信封和确认凭据的机械鉴权；
- 守住点击确认、停止、迟到失效、刷新恢复和敏感值本地填回。

内核不做：

- 不识别取消、问候、闲聊、改口、补充、缺项或业务意图；
- 不读取含义包、卡片 DTO、模块字段或错误事实的业务含义；
- 不判断模块参数是否正确、业务是否办完、谁有业务权限或谁应负责；
- 不把模型步骤当命令，不直接读写业务数据；
- 不根据模块数量、字段或流程增加业务分支。

#### 超级大脑：唯一自然语言理解者

第一次调用负责理解老师要做什么、候选模块、候选参数、单模块内部候选步骤及是否需要澄清，返回 MeaningV1。它不执行任何动作，也不能生成可执行凭据。

第二次调用只在需要时把模块提供的模型安全结果组织成老师听得懂的话。它看不到系统持有的敏感值，不能修改模块事实、正式终态或权限结论。

模型的思考过程是黑盒。前端、后端和日志只保存协议结果与必要诊断，不展示或保存思维链。

#### 业务模块：业务唯一所有者

模块只懂自己的业务，负责：

- 验证超级大脑候选是否属于本模块、字段依据是否来自老师原话、参数是否合规；
- 维护本模块私有草稿、状态、权限关系和事实；
- 用服务端当前身份、任职、学校、范围、责任关系和业务版本二次鉴权；
- 返回缺项、拒绝、结果、卡片、待确认动作和模型安全上下文；
- 点击确认后再次鉴权，以幂等、事务和审计方式执行正式动作。

### 2.3 完整运作链

#### 普通自然语言回合

老师说话
→ 内核接纳本句并记录因果位置
→ 内核用模型安全上下文、当前原话和已安装模块的静态能力说明调用超级大脑
→ 超级大脑返回 MeaningV1
→ 内核只验外壳，并按唯一 module_ref 把 ModuleCallV1 整包交给模块
→ 模块验证候选、二次鉴权并处理，返回 ModuleResultV1
→ 内核按 direct、precomposed 或 compose 三档呈现
→ 内核把结果落回原回合并呈现给老师。

#### 无对应模块或需要澄清

超级大脑返回 clarify 或 none 时，内核不猜模块、不查关键词、不调用业务模块。内核只把该协议结果交给超级大脑的表达出口，说明需要老师补哪一句或说明当前还不能办理。表达调用失败时使用固定技术兜底，不把“模型失败”伪装成“业务不支持”。

#### 正式动作

模块先返回 action_offer
→ 内核呈现确定性确认按钮
→ 老师点击
→ 内核重新校验会话、对话、回合、模块和一次性确认凭据
→ 模块按当前服务端事实再次完成业务鉴权
→ 模块用幂等键和事务执行
→ 模块返回真实成功、明确失败或结果未知
→ 内核按受限呈现规则显示结果。

AI、老师自然语言和卡片文本均不能替代这次点击。

### 2.4 模块静态目录与挂接准入

第一阶段使用代码内静态目录，不建设运行时注册中心或多应用路由平台。

每个已接入模块只登记：

- 稳定且不含业务数据的 module_ref；
- 模型安全的最小能力说明；
- MeaningV1 中本模块候选参数的形状说明；
- ModuleCallV1 和 ModuleResultV1 的协议版本；
- 模块处理入口和确认入口；
- 模块声明的字段名集合、呈现能力和 action_offer 能力；
- precomposed 可使用的受限文字片段、允许模板版本和确定性 fallback 版本。

只有已经实现、通过模块自动门和用户 checkpoint 验收的模块才进入静态目录并随第一次模型调用提供能力说明。14 个候选模块中尚未完成的模块不得提前登记，否则超级大脑会把请求路由到不存在的能力。

能力说明是随代码发布的静态、模型安全文字，只说明“能处理哪类请求”和“候选参数叫什么”。它不得读取当前登录人、任职、权限、数据库、通讯录或运行期结果；所有用户看到同一份能力说明。能力说明进入模型只表示系统有这种能力，不表示当前老师有权限，权限仍由模块根据服务端当前事实判断。

### 2.5 核心协议

#### MeaningV1

MeaningV1 是第一次超级大脑输出的候选含义包，外壳固定包含：

- version；
- conversation_ref、turn_ref、run_ref；
- mode：dispatch、clarify、none 三态之一；
- dispatch 时恰好一个 module_ref；
- meaning_payload：模块私有候选含义，对内核不透明；
- evidence_refs：指向当前老师原话的字符区间或逐字依据，由模块验证；
- candidate_steps：同一模块内部的候选意思顺序，不是命令；
- precomposition_candidate：基于模块已声明字段名和受限文字片段生成的候选回复模板，可空；
- model_safe_expression_input：clarify 和 none 时必填、dispatch 时可空，作为第二次表达调用的安全说明输入；内核只验其存在、类型和大小，不解释内容。

内核只检查 JSON、版本、必填项、大小、枚举、恰好零或一个模块句柄以及引用边界；不判断候选含义是否正确、参数是否齐全、步骤是否合理。dispatch 的整包只能交给一个模块。

#### ModuleCallV1

ModuleCallV1 由内核机械封装，包含：

- 协议版本和 module_ref；
- conversation_ref、turn_ref、run_ref；
- 服务端签发的 actor_context_ref；
- 当前老师原话；
- 原样的 meaning_payload、evidence_refs 和 candidate_steps；
- 模块私有状态引用及 revision；
- precomposition_candidate。

actor_context_ref 只是服务端当前上下文的不可伪造引用，不把人员、任职、电话、角色或权限事实送进模型。模块必须自行解析并重新读取当前事实。

#### ModuleResultV1

ModuleResultV1 外壳固定包含：

- validation_receipt：accepted、needs_input 或 rejected，以及可公开的安全结果族；
- locked_notice：当前存在不可被本回合静默覆盖的草稿、待确认动作或正式终态时的模块安全说明；
- staged_state_ref 和 state_revision；
- capsule_update：unchanged、replace 或 clear 三态；只有 replace 必须且只可携带 model_safe_capsule，unchanged/clear 不得夹带 capsule；
- presentation_mode：direct、precomposed 或 compose；
- display_kind：text 或 card；表格、列表等只能是 card DTO 的内部布局，不形成第四种顶层呈现；
- 对应档位的 display_payload，或 display_template + field_map，或 model_safe_narration + 中性 slot_map；
- precomposed 和 compose 必须提供模块确定性生成、独立于模型候选的 fallback_presentation；
- model_safe_note；
- action_offer，可空；
- recovery_control，可空；
- result_check_handle，可空；
- safe_error_projection 和 diagnostic_ref，可空。

模块原始异常、私有状态、业务 DTO 和敏感字段不能因为装进 ModuleResultV1 就自动变成可送模型内容。只有独立的 model_safe_narration、model_safe_note 和 model_safe_capsule 可以进入模型安全通道。

validation_receipt 是模块对第一次候选的验证结果。第二次表达模型可以知道“候选已接受、需补充或被拒绝”以及模块提供的安全说明，但不能看到权限依据、内部异常或敏感业务值，也不能把被拒绝的候选包装成已完成。

### 2.6 三档呈现

direct、precomposed、compose 是“结果如何生成”的三个档位，不是新的界面类型。第一阶段顶层呈现只允许文字、卡片、确认动作三种：文字和卡片由 display_kind 锁死，确认动作只由独立 action_offer 表达。表格或列表若需要，只能作为 card DTO 内部布局，不能要求内核新增第四种呈现类型。

#### direct

适用于卡片（内部可使用表格或列表布局）、通讯录、班级学生、受限制度正文、含多项敏感值的结构化结果以及必须保持精确的结果。模块 DTO 直接进入展示账本，零第二次模型调用。

direct 结果不得自动写入模型安全账本。后续连续性只使用模块另给的 model_safe_note 或 capsule；缺失时宁可少给上下文，也不能把卡片 DTO 或可见文本倒灌模型。

#### precomposed

适用于结果字段可预测、短而确定、适合固定结构的回复。第一次超级大脑可依据模块声明的字段名集合和版本化受限文字片段产生 precomposition_candidate；模块取得真实结果后决定是否采用，验证通过才返回：

- 经模块确认的 display_template；
- field_name 到本地真实值的 field_map；
- 独立 model_safe_note；
- 模块确定性生成的 fallback_presentation，模式校验失败时不再调用模型。

内核只按字段名精确匹配并机械填入，不读取字段值含义。字段名可以被模型看见；字段值不得进入模型。

precomposed 的字面文本不能任意自由生成。每个模块只为实际出现的少量结果族维护固定片段或版本化模板，通常控制在 4–8 条；公共 PresentationBuilder 只共享 envelope、槽生成、集合校验和账本分流，不共享业务话术。

#### compose

只在复杂、非敏感、确实需要自然组织的结果，或老师可自行补正的缺项/歧义中使用。模块必须显式选择 compose，并同时提供：

- 最小 model_safe_narration；
- 含中性随机槽的安全模板；
- 本地 slot_map；
- 第二次模型失败时的 precomposed fallback。

第二次模型只组织句式。返回后内核机械校验中性槽多重集合完全一致，再在本地填值。漏槽、增槽、重复槽、超时或格式错均零重试，直接使用 fallback。

#### 字段名模板和敏感槽的机械规则

1. 字段声明分为模型可见字段名、固定展示标签和模块内部真实字段；数据库列名不得直接暴露。
2. precomposed 模板只能引用当前操作声明的字段名，不得发明新字段。
3. 模块返回的 field_map 键集合必须与模板占位符集合一致；缺项、多项、重复或未声明字段均使候选呈现作废并使用模块随结果提供的 fallback_presentation。fallback 缺失或自身不合协议时，整个 ModuleResultV1 失败关闭，staged update 不结算，只显示固定技术失败说明。
4. 第一次模型在模块查询前生成模板，不会取得真实字段值；模块仍须检查模板字面部分只来自本操作的版本化允许片段，防止模型自行编造事实。
5. compose 对模型可见的值槽只使用随机中性编号，例如 S1、S2；slot_map 只留在服务端本地。
6. 填值后的文本只进入展示账本，不得进入模型安全账本、下一轮模型请求、普通日志或异常。
7. 若把一个操作的内部字段句柄在声明、MeaningV1 模板和 ModuleResultV1 field_map 中一致重命名，内核的校验、路由、填值和日志结构必须不变。该测试用于证明内核只是匹配字符串，不理解字段含义。

字段类别和字段名不是敏感值；具体姓名、号码、原因、成绩、关系、任职、范围和记录内容才是系统持有的值。第一阶段接受模型知道“这里有一项联系电话”之类的结构信息，不接受真实值泄漏。

API 调用费用由学校承担。第一阶段只通过 direct/precomposed、零自动重试和不额外总结历史来避免无效调用；费用不是取消大模型理解或否决必要 compose 的理由。

### 2.7 一句话一模块

第一阶段每个自然语言回合最多投递一个模块。超级大脑可以识别一句话包含多个候选事项，但只能返回 clarify，要求老师一次说一件事；内核不拆成多模块命令、不并行、不串行执行跨模块步骤。

candidate_steps 只是一个模块内部供其验证的候选意思顺序。内核整包转发，模块可以接受、拒绝或要求补充，不能把模型步骤直接当成正式命令。

复杂但属于单一模块的请求应优先交该模块验证。若超级大脑无法确定 module_ref，则返回 clarify；表达出口提出一次低成本确认。老师的确认句仍作为新的自然语言回合再次经过超级大脑，内核不把“对”自行解释成确认。

### 2.8 对话、上下文和三账本

每个对话拥有独立 conversation_id，不继承其他对话的历史或模块状态。同一老师可以建立多个对话，但各对话互不认识；第一阶段不做跨对话记忆。

每个对话分开维护：

1. 因果账本：conversation、turn、run、generation、request_id、状态、时间和结果引用，只服务一次一句、busy、stop、刷新和迟到失效。
2. 展示账本：老师原话、最终回复、卡片、填入敏感值后的文本和可见状态，只用于恢复老师界面。
3. 模型安全账本：老师原话、固定技术标记、模块独立提供的安全 note、填值前安全模板，以及每个仍有活动私有状态的模块各自最新一份安全 capsule。

模块真实草稿、权限事实、敏感值、slot_map 和正式业务数据留在模块侧；内核只保存模块私有状态引用和 revision，不解析内容。

第一次模型上下文按固定顺序组装：

1. 固定系统提示与 MeaningV1 格式；
2. 已安装模块的静态模型安全能力说明；
3. 当前对话内所有活动模块最新已提交的 model_safe_capsule，按 module_ref 固定排序；
4. 预算内最近的完整模型安全回合；
5. 当前老师原话。

模块完成或取消当前私有状态时，必须返回 `capsule_update=clear`；内核按 module_ref 和 revision 机械保留、替换或删除，不理解内容。每份 capsule 使用同一个固定大小上限，第一阶段最多只有 14 个已安装模块，协议为全部活动 capsule 预留总预算；新结果若使该固定总预算超限则失败关闭，不能静默丢掉某个模块的续接状态。

当前原话和全部活动 capsule 不截断。普通历史超预算时从最旧完整回合开始剔除，不截半句话、半个 JSON 或半个模板；不额外调用模型总结。展示账本永不作为模型历史来源。

此前模型未经模块确认的候选不能作为事实回灌。只有模块接受并随已完成回合提交的安全 capsule 和 note 可以影响下一轮理解。

### 2.9 一次一句、busy、停止与迟到

每个对话同一时刻最多一个 active_run；一次一句只约束一个对话，不代表全校请求串行。

系统思考时：

- 输入框保持可见，可以先打字；
- 发送暂不可用，不接纳第二句、不建立隐藏队列；
- 多标签页或重复发送由服务端原子返回 busy；
- 未被接纳的文字留在输入框，不进入任何账本。

stop 是机械按钮，不是自然语言，不调用模型。确认前 stop 被接纳时，当前回合 generation 立即失效；第一次模型、模块 staged 处理、第二次模型、卡片、回复和 capsule 全部作废。供应商请求未必能物理撤回，但迟到结果不得结算、显示或复活。

老师原话保留在展示历史并标为已停止；模型安全历史最多保留该原话和 stopped 技术标记，不保留未确认 meaning、模块结果或 capsule。

模块在确认前只能返回 staged update。只有当前 run 仍有效并完成全部链路时，内核才一次性结算模块状态引用、capsule 和呈现，避免“状态已改但老师没看到”。

老师点击正式确认后不再提供 stop。正式事务是否已写入不能由前端取消来判断；此后只有真实结果。

### 2.10 错误表达链与屏蔽

模块可自行修正且不含受保护事实的缺项、格式不合格和歧义，可以通过 safe_error_projection 进入 compose，由第二次超级大脑组织解释。

以下结果必须 direct 或固定 precomposed，不能交模型自由改写：

- 未登录、无权、跨校、任职或责任关系失效；
- 受保护对象不存在或无权查看；
- 正式动作成功、明确失败、结果未知；
- 幂等冲突、版本冲突、事务失败；
- 数据库、网络、模型供应商、超时和依赖故障；
- 安全拒绝、审计失败和敏感数据异常；
- 通讯录、班级学生、受限制度正文等敏感结构化结果。

原始异常、堆栈、SQL、表列、约束、HTTP 请求响应、供应商错误体、密钥、Token、RLS 上下文、actor、角色、任职、责任范围、人员目录和完整业务 DTO 永不进入模型或老师页面，只进入受控诊断链。

第一次模型失败或 MeaningV1 格式不合格：不调模块、不改状态、不猜含义，显示固定技术说明。

模块崩溃、超时且没有安全错误投影：staged update 不提交，显示固定技术说明“现在暂时没能完成这次处理，请稍后再试。”，不能把异常对象交模型。

第二次模型失败：不改变模块已确认事实，在回合仍有效时使用模块随结果提供的 fallback；不能把成功改写成失败。

### 2.11 语言取消和机械放弃

老师说“取消、算了、不办了”仍是自然语言，必须经过第一次超级大脑；内核不维护取消词表。超级大脑返回唯一模块句柄和候选取消含义，模块根据当前私有状态决定能否取消。

语言取消成功后，模块生成新 revision 和新 capsule；上一 revision 签发的 recovery_control 必须同时失效，界面按 artifact 引用收起旧控件，不能留下老师点击后才发现过期的按钮。

模块存在未提交状态时可以返回 recovery_control。它绑定 conversation、模块状态 revision 和一次性 nonce，界面显示“放弃当前未提交内容”。点击是机械控制，不调模型；模块重验仍为同一未提交版本且没有正式影响后才清理。

机械放弃只清理模块声明的未提交 artifact，不删除普通对话历史，不撤销已保存数据，不适用于正在执行的正式动作。模型故障时语言取消可能无法理解，recovery_control 是确定性逃生口。

### 2.12 正式确认、幂等与结果未知

action_offer 由模块签发，绑定当前 actor_context_ref、conversation、module_ref、模块状态 revision、明确动作摘要、过期时间和一次性 nonce。模型和前端不能生成或修改可执行 token。

点击后内核只做五项机械检查：

1. 当前服务端登录会话有效；
2. conversation 属于当前登录上下文；
3. turn、run、generation 和 request_id 当前有效且未重放；
4. module_ref 是当前已安装模块，信封版本有效；
5. action_offer 绑定当前上下文、模块和 revision，未过期、未消费，且本次来自一次真实点击。

模块随后做六项业务检查：

1. 当前身份和任职仍有效、未撤销、未过期；
2. 当前任职具有该模块动作权限；
3. 操作者、目标和新数据处于允许学校边界；
4. 当前人有权读取或引用目标对象；
5. 当前责任、主体或归属关系仍成立；
6. 当前业务状态、版本和待确认内容仍允许该动作。

正式执行使用幂等键。成功、明确失败和结果未知是三个不同终态；超时不能谎报失败或成功。

结果未知时模块返回 result_check_handle。该句柄绑定原 action_id、幂等键、actor_context_ref 和模块，只允许读取权威终态，绝不重新执行动作。老师点击“核验结果”后，内核和模块重新鉴权；若已确定则呈现唯一真实结果，仍未知则继续明确说明，不要求老师重复提交。

三类公开点击凭据和预建核验凭据统一固定有效 300 秒。Redis 只保存短寿命凭据登记并依靠 TTL 自动删除；过期本身绝不续期、重建或重新启用动作。未决核验凭据到期后，运行时机械收起按钮并把展示状态改为“待人工核对”，不调用模型，也不自动生成新句柄。只有老师再次真实点击尚未过期的核验按钮且模块仍返回未知，才可签发新的 300 秒 result_check_handle。

正式 action 点击中，服务端 confirmation_ref 同时是模块 confirm 的幂等引用和预建 `check_result` 的 result_check_ref。内核在调用模块前，以 Redis Lua 原子消费原点击凭据并登记隐藏核验凭据，同时在运行时建立机械 reservation；reservation 阻止新 run 和并发点击，但 Python 锁不得跨 Redis、模块、数据库或网络调用持有。隐藏核验按钮不提前展示；只有模块结果未知、模块调用不确定，或调用后的持久化、呈现、运行时结算失败时才显露。明确成功或明确失败清除隐藏凭据。旧 action/check 凭据始终保持已消费，核验点击只调用 check_result，绝不重新进入 confirm；刷新只能恢复已经显露的待核验控制。

### 2.13 权限与敏感边界

超级大脑不得取得：

- 服务端当前人的真实身份、登录映射、任职、岗位、角色或权限；
- 学校、组织、班级、责任组和数据范围的运行时事实；
- 通讯录、电话号码、学生名册、成绩、纪律记录、请假理由等系统持有值；
- 卡片 DTO、direct 结果、填槽后的文本、数据库标识和内部异常；
- action_offer、recovery_control、result_check_handle、幂等键或写入凭据。

老师原话逐字进入第一次模型，即使老师自行写了姓名或号码；系统不宣称对老师原话做了脱敏。系统仍不得从其他来源重复注入同一值。

能力说明和字段名可以进入模型，因为它们只描述能力外壳；运行时值不能进入。

受控对象选择器必须由所属模块在服务端按当前 actor、动作、学校和范围先裁剪，再返回前端。前端只收到 choice_handle、最小显示名称、必要区分提示和不透明游标；每页最多 20 项。选择后和正式确认前均重新鉴权。全校学生名单、全量地点或未裁剪候选不得下发前端，选择器查询、候选和结果均不得进入模型。

若某模块确有不同分页上限，必须在该模块九项模板第一遍中定死，不能在实现时自行修改。

### 2.14 三层系统边界

#### 内核

拥有对话、三账本、active_run、模型调用编排、协议外壳、模块句柄转发、三档呈现、stop、点击确认和本地机械填槽。内核不拥有学校事实或业务状态。

#### 学校共享技术服务

拥有学校事实 Schema、正式 Excel 导入、可信身份与上下文、PostgreSQL/RLS、事务、幂等、审计、Outbox、模型供应商适配和必要文件能力。

学校事实层只保存跨模块共享的权威事实：学校/校区、人员与登录映射、组织、任职及有效期/撤销、地点层级/别名/历史、住宿、联系方式及可见性、制度资料版本/分级/有效期及适用范围、导入来源和版本。

学校事实层不声明“谁能报修、谁该维修、谁能审批请假、谁负责卫生”。岗位名称和任职事实不等于模块权限；Governance 保存经正式授予的长期职责事实，Module Policy 把现实关系或治理职责映射为模块 action，模块自己的状态关系仍由模块拥有。

#### 业务模块与应用侧适配器

模块拥有业务字段、状态机、action 词典与 Module Policy、模块自己的状态关系、资源 Reader、Handler、卡片、模板、草稿、正式动作和历史；模块不得保存第二份治理职责事实。适配层只把模块形状翻译成内核协议，不把业务语义写进内核。

超级大脑是内核调用的外部理解与表达能力，其供应商配置留在集成层；模型不是业务模块、权限源或操作者。

#### 权限层与治理职责域的五层结构（冻结）

第 2.14 节的三层是系统所有权与部署边界；下面五层进一步冻结学校现实、治理职责、模块动作规则、授权执行和模块状态之间的语义分工，不新增运行时层级，也不表示五层都已形成生产可用能力。SF5A 已实现 Governance authority 与未挂生产的 Thin Authorization 最小纵切；SF5B 已实现数据库硬门、隔离 Writer 与底层 R1 Reader/Projection 机制，但生产读取 operation registry 仍为空，Module Policy、产品 Reader/Projection 和正式 action 接线仍未实现：

1. **School Facts：**保存学校现实关系，包括人员、组织、任职、校区、地点，以及将来的班级、班主任、任教学科等。School Facts 不声明任何具体业务动作权限。
2. **Governance（学校治理/授权事实域）：**保存“哪一个任职被正式授予哪一项职责、负责什么范围、从何时生效到何时结束、依据、是否撤销”。职责词典由 Governance 拥有。
3. **Module Policy：**模块拥有自己的动作词典和动作规则，把 School Facts 的现实关系或 Governance 的治理职责映射为该模块的 action；Module Policy 不保存职责事实本身。
4. **Thin Authorization（薄权限执行层）：**只负责取得可信 actor 与履职上下文，调用 action 所属模块的 Policy，组合职责、现实关系与 Scope，返回 `allow/deny + ScopePlan + Projection`，设置数据库安全上下文，并执行撤权重验与授权审计。Thin Authorization 不拥有模块数据、业务状态机或资源查询逻辑，不是通用 Reader。
5. **Module Data：**工单负责人、审批人、事件处理人等模块自己的状态关系留在各模块，不能提升为 School Facts 或 Governance 的通用事实。

#### Governance 的四笔账

1. **信任等级账。**Governance Grant 必须与 School Facts 同级可信，但不必复用 School Facts 的整套表与写核。两个域共享 Unit of Work、幂等、审计、版本和 PostgreSQL 约束等底层原语；Governance 可以拥有自己的窄变更账本或 grant-version 历史。现在不提取公共 change-unit/lineage 抽象，不做形式统一；Governance 不得冒充 School Facts 第 20 类。
2. **职责词典归属账。**职责词典由 Governance 拥有，动作词典由各模块拥有，模块只定义“职责或现实关系如何映射为模块 action”。Governance 不得保存模块 action，模块不得自造第二份职责事实。
3. **旧授权域归宿账。**`platform/authorization` 收缩为 Thin Authorization 和平台技术权限层，只保留 `system_admin`、平台配置、技术运维权限等技术含义，不再拥有业务 action 含义、治理职责权威或模块完整数据查询。既有 `roles`、`user_roles`、`role_permissions`、`responsibility_scopes` 按含义分流：技术权限保留；已经编码业务含义的 role/action 冻结新增并逐 action 迁移到 Module Policy；学校长期分工内容迁移到 Governance；临时兼容项必须标记 legacy。`platform/responsibility` 在业务所有权上逻辑归属 Repairs；本轮不移动目录、不改表名、不搬表，且 Governance、School Facts 和其他模块不得把它当通用责任体系。“长期负责全校维修”等既有内容以后逐项判断归 Governance、Repairs 或 Repairs 业务状态，不整表搬家。
4. **任职与职责授予失效账。**Governance Grant 绑定 `assignment_id`，不直接绑定 `person_id`。一项职责有效必须同时满足：Grant 有效、任职有效、人员根有效、组织根有效、范围目标有效。任职结束或撤销、人员停用时，查询必须失败关闭，不做批量级联写；其他任一依赖失效也同样失败关闭。旧授权快照必须通过 security epoch 或等价机制立即失效。

#### 两条不可绕过的规则

1. **单 action 单权威。**同一 action 在任一时刻只能有一个授权权威。迁移必须逐 action 完成“旧模型权威 → 一次性迁移与验证 → 新模型权威 → 关闭旧模型解释权”；禁止使用“旧模型允许或新模型允许就通过”的并集逻辑。
2. **每域一个写核。**School Facts 与 Governance 各恰好一个写核，互不越界。共享的是 Unit of Work、幂等、审计、版本和 PostgreSQL 约束等底层原语，不是共享一套 ChangeSet 或 lineage 表。不得因为存在两个域而开第三个旁路，也不得用“唯一写核”否认 Governance 拥有独立写核。

#### Governance Grant 的领域语义、待决边界与 bootstrap 原则（冻结）

##### Governance revoke 的领域限定

Governance Grant 的 `revoke` 是 **prospective withdrawal**：从正式撤销时点起向未来撤回该职责授权。撤销前真实存在过的历史授权状态继续保留，不得被解释成“从未授权”；原计划结束时间不得因 revoke 被覆盖。Grant 一经 revoke 不得 reactivate；未来再次正式授予时必须建立新的 Grant 身份。

若未来需要表达“该授权从一开始就不应成立”，那是独立的追溯纠错语义，不属于普通 Governance revoke；该追溯纠错语义仍未定义、未实现。School Facts 的 `revoke` 继续遵守 Checkpoint 3 已冻结的现有权威语义，不重新定义、不重开 Checkpoint 3，也不因为两个领域使用同一英文操作名就推断它们完全同义。SF5A 已实现的 Contract 与类型显式表明操作对象是 Governance Grant，不使用脱离领域的裸 `revoke` 含义；当时的语义冻结轮次没有修改任何 API 或代码。

##### Grant 核心绑定与授予依据所有权

Grant 的 `assignment` 与 `duty` 是授权身份的不可变核心绑定，不得通过 update 把既有 Grant 原地换成另一个 assignment 或 duty。正常调整、替代或自然结束使用正式 `end` 结束原 Grant，再为新的 assignment 或 duty 建立新 Grant；正式撤回使用上述 prospective `revoke`，确有重新授予需要时建立新的 Grant 身份。`end` 与 `revoke` 不是可互换的同义操作，必须保留各自的治理语义和审计意义。Scope 变化是否也必须创建新 Grant 仍未决定。

Governance 只拥有授予依据的稳定引用，不拥有依据正文。它不得因记录授予原因而扩展成公文正文库、制度正文库、附件仓库或通用文档管理系统。完整依据正文未来由哪个权威域拥有尚未决定；Governance 只需稳定指向正式依据，使引用可审计、可追踪、可解释。

##### Scope 未决边界与 revision 19 硬门

下列 Scope 产品与架构语义继续保持未决：

1. Scope 有哪些正式目标类型；
2. 是否支持组织层级后代；
3. 是否支持地点层级后代；
4. 一个逻辑 Scope 是否可以包含多个目标；
5. 多目标的组合语义；
6. Scope 是否动态跟随组织或地点层级变化；
7. Scope 扩大或缩小时，是 update 原 Grant、end 原 Grant 后新建、revoke 原 Grant 后新建，还是采用其他正式语义。

`revision 19` 不得通过固定 Scope 枚举、永久性唯一约束、排除未来合法模型的 CHECK、把“一个 Scope = 一个目标”写死成不可演化物理事实、写死层级继承或 Scope 变更语义，提前替用户冻结上述未决事项；也不得使用万能 `target_id` 后仅靠应用层猜测目标类型。

本边界不否认数据库安全约束。对不涉及未决产品语义的已确定通用不变量，后续仍可根据证据设计必要的 PostgreSQL 约束，例如同校一致性、必填字段非空、稳定引用完整性、合法时间区间、正版本、必要引用存在和拒绝明显无效状态。原则是数据库保证已确定的不变量，但不替用户决定未确定的产品语义。

##### 并行 Grant 未决且歧义必须失败关闭

当前尚未批准“同一 assignment + duty + Scope 是否可以存在多个同时有效、来自不同独立依据的 Grant”的生产语义。在真实授予依据和学校治理规则确认前，物理实现不得用永久唯一约束提前排除未来可能；授权裁决也不得任选一条、以“任一 Grant allow 即放行”求并集、自动合并 Scope，或允许不同 Reader / Policy 各自解释。

若同一授权关系出现多条同时有效、且按当前已批准规则无法得到唯一解释的 Grant，必须视为授权歧义并 fail closed / deny，不得猜测。该硬门具体由 Governance Reader、Thin Authorization、Module Policy、Writer、PostgreSQL 或其组合中的哪一层执行，在当次语义冻结中留待后续物理设计、未于该轮冻结实现位置；后续 SF5A 物理设计现已完成，本次状态补正不重述或修改其结论。

概念上，“并行 Grant”可能表示同一 assignment + duty + Scope 因不同独立正式依据而在同一时段同时有效；“重新授予”则是旧 Grant 已 revoke 后创建新 Grant，旧、新 Grant 不在同一有效时段。前者只登记为待决概念，尚未批准为当前生产能力；后者已经冻结为重新授予语义。

##### 外部 Governance bootstrap 原则

首批 Governance 管理能力必须由 Governance 权威域之外的受信任平台 bootstrap authority 建立，以解决 Governance 尚无内部管理授权时首批治理能力的来源。Governance Writer 在 bootstrap 期间仍必须执行授权校验，授权来源改为该外部平台级受信任 authority；不得因为“尚无第一条 Grant”临时关闭鉴权或保留裸写入口，也不得默认 Governance 自己凭空生成角色、校长天然有权、系统管理员永久有权修改全部 Grant，或留下长期超级管理员旁路。

外部 bootstrap authority 至少必须满足：

1. 最小权限；
2. 明确 bootstrap 状态；
3. 完整审计；
4. 幂等；
5. 可明确关闭；
6. 关闭后不得继续形成常规 Governance 写入旁路；
7. 不依赖编造生产 duty dictionary；
8. 不把 test-only duty 当作正式学校职责。

当时的语义冻结轮次不决定 bootstrap 是 CLI、部署命令、平台 technical permission、窄数据库函数还是一次性 token，不决定是否注入第一条 Grant、是否建立多条首批管理能力、具体调用者、具体表或字段，以及关闭机制如何实现。后续 SF5A 实现选择复用既有 `campus_ai_migration` 部署信任面，通过唯一 Governance Writer 和持久状态完成可审计、幂等、可关闭 bootstrap；没有新增 CLI、HTTP、token、数据库函数或裸写入口。

#### 当前权限原型目标与未知项

当前不依赖 Governance 职责事实的最小权限原型目标只有下列四类，而且都不是当前小静的生产可用能力：

- 本人当前任职：可以基于现有 Reader 验证；
- 公开地点：可以基于现有 Reader 验证；
- 官方办公联系方式：SF5B 已实现只选 official contact 固定列的窄 Reader/Projection 机制；生产 operation registry 仍为空，故不得宣称产品纵切或正式查询已经跑通；
- restricted 制度正文：可以先验证“读取前固定拒绝”，不得宣称制度查询链已经完成。

“有明确职责者按范围查询”和“谁负责某学生/宿舍范围”缺少当前权威职责与范围输入；不得用测试 fixture 假装产品已经具备这两项能力。

职责词典的正式内容必须来自真实学校的组织、任职、地点结构和具体模块设计时的实际职责需求，并由用户或校方明确确认。SF5A 实现没有填充任何正式 `duty_code`。在真实结构和模块需求明确前，生产职责词典保持空；允许使用明确标记为 test-only 的虚构 fixture 验证机制，但 fixture 不得进入 migration seed、默认配置、生产文档或产品宣传。职责词典最迟在首个依赖治理职责的真实查询或业务模块实施前拍板。

#### SF5 起的冻结顺序、revision 归属与完成边界

SF5 起的正式实施顺序冻结为：**SF5A → SF5B → SF6 → SF7**。SF5B 不是完全独立于 Governance 的整体：其中 importer/runtime 写入硬门以及部分不基于职责的 Reader/Projection 不依赖 SF5A；但“有职责者按范围读取”的 Reader/Projection 必须消费 Governance Grant、Thin Authorization、`ScopePlan` 与 `Projection`。因此完整依赖方向是“Governance 正式授权权威 → Thin Authorization → Reader/Projection/ACL/RLS 等硬门 → 候选学校正式导入 → 最终验收”。“SF6 技术上可以不依赖 SF5A”不等于“SF6 应排在 SF5A 之前”；顺序依据完整权限边界冻结，不为保留旧 migration 编号让路。

`revision 19` 唯一归属 SF5A 所需的生产持久化数据库变更；`revision 20` 归属 SF5B 所需的数据库层变更。原“`revision 19` 属于 SF5B importer ACL”的当前口径不再保留双重解释，也不创建空 migration 兼容旧说法。编号归属本身不表示 SF5B 的全部能力都必须通过 migration 实现；本轮后续拍板已在第 2.19 节冻结 DB-school anchor、tenant RLS、同校 Scope R1 与隔离 Writer Executor 的安全边界，但未冻结其具体数据库对象、IPC 或实现文件。

SF5A 的完成标准不是只让授权算法或 process-local fixture 跑通，而是生产 Governance authority 已持久化并满足冻结的生产性质：Governance 与 School Facts 保持两个同级可信且互不越界的权威域；Governance 拥有唯一正式写核并复用平台 UoW、幂等、审计、版本与 PostgreSQL 约束等基础能力；Grant、assignment、person、organization 与 scope target 的联合有效性在查询时失败关闭；Grant revoke 后新事务可重新读取撤权结果，旧授权快照通过 security epoch 或等价机制立即失效。SF5A 不拆成独立的“内存机制版”和“生产持久化版”两个 checkpoint。

明确标记为 test-only 的虚构 duty/grant fixture 仍可用于 TDD 和机制验证，但不形成 SF5A-lite，不属于生产职责，不得进入生产 seed、默认职责词典、正式学校配置或产品宣传。生产职责词典在取得真实学校结构、实际职责需求和用户或校方确认前继续保持空。

当时的文档冻结任务只冻结顺序、revision 归属、SF5A 生产完成标准与 SF7 验收边界；该轮没有创建 migration，也没有设计 Governance 表、字段、索引、约束、ledger/history、grant-version、security epoch 具体实现、Writer 内部结构或 SF5B 的具体 RLS/ACL/Reader/Projection 形态。该历史边界不应被误读为当前实现状态。

#### SF5A 实际实现结果（已正式通过复阅）

SF5A 使用唯一 `apps/api/alembic/versions/20260823_19_governance_authority.py`，在独立 Governance authority 中持久化 duty、Scope、Grant 的稳定身份与版本切片，以及 assignment epoch、bootstrap 状态、命令回执和 typed audit，共 10 张物理表；没有 revision 20。生产 duty、Scope、Grant 与 bootstrap 状态默认全空。runtime 对 Reader 所需 7 张 authority 表只有最小 `SELECT`，对 10 张 Governance 表均无直接 DML，对 receipt、audit、bootstrap 支撑表也无读取权；没有修改 School Facts、legacy authorization 或 repairs-owned responsibility 的 ACL/RLS/catalog。

Governance 只有一个正式 Writer，统一执行 duty/Scope create、Grant create/update/end/prospective revoke 和 bootstrap open/close，并在同一 PostgreSQL 事务写 authority/version、assignment epoch、幂等回执和审计。Grant 的 assignment+duty 不可原地更换；revoke 保留历史与原计划结束时间、禁止 reactivate，再授予必须创建新 Grant。Reader 与 AuthorizationBasis 支持 current、as-of、future-effective、planned end、end/revoke 与 fresh revalidation；assignment、person、organization、Scope owner 任一缺失、失效、错误、版本零或并行 Grant 歧义均 fail closed。

School Facts 依赖只经 composition 的 owner-provided 窄 Reader/Repository 适配器取得 assignment、person、organization 的有效性与版本；Scope 使用注入的类型化 owner resolver。Governance 核心没有跨域 ORM JOIN，也不调用 School Facts Writer、ChangeSet 或 lineage。Scope 以稳定 identity、版本化 schema owner/name/version 和规范引用/摘要承载，未固定产品 Scope 枚举、层级、多目标或 Scope 变化生命周期；数据库也未用永久唯一约束排除未来可能的 parallel Grant。

Thin Authorization 只接受可信 `StaffActorContext` 与匹配的履职 assignment，调用注入的 Module Policy，并返回确定性的 allow/deny、类型化 `ScopePlan`、命名 `Projection` 与可重验 `AuthorizationBasis`；Projection 不携带敏感值，ScopePlan 不携带任意 SQL。该纵切没有挂入 `app.main`、assistant、repairs、旧 authorization router 或任何生产 action；旧 RBAC 和 responsibility 仍无 Governance 解释权。SF5A 已正式通过复阅，批准提交为 `[私有历史提交]`；后续 SF5B 也已完成实现、仓库 Level A/B 证明和用户正式批准，不得自动进入 SF6/SF7。

#### SF5A 非阻塞后续风险

- **Scope 写时语义校验：**当前 Scope 的 schema identity、reference document 与 owner semantics 的语义一致性主要由 owner resolver 校验，现有设计可接受且不阻塞 SF5A。未来增加真实 Scope 类型后，需要复核是否应将更多 Scope schema/reference 一致性校验前移到正式 Writer 写入阶段；该风险登记不改变现有 Scope、Grant 或 Writer 语义。
- **Bootstrap 与数据库根权限：**Governance bootstrap 的“永久关闭”只表示 Governance bootstrap command path 永久关闭，不表示消灭 migration/DB-owner 的数据库根权限。后续生产部署与运维安全基线必须保证 migration/DB-owner 凭据与 runtime 严格隔离，不进入普通应用容器或普通 runtime 配置，不成为日常 Governance 写入旁路，也不作为学校管理员的常规操作能力；该风险登记不改变现有 bootstrap 实现。

四项特殊边界：

1. 个人联系方式默认只供本校已登录人员查询，同意记录编号是可选来源证据，不是扩大范围的必填前提；定向范围仍必须声明受众，任何查询都先在服务端按当前人裁剪。家长查看当前班主任联系方式的能力在班级、监护关系和班主任事实补齐前保持关闭。学校官方值班电话是独立官方资料，不冒充个人联系方式。

3. 内务、卫生模块的检查方不是由内核或岗位名称自动推断。模块配置把当前有效任职映射到检查动作和范围；责任对象只可查看和提交自己范围内整改，复核人按独立复核权限确认，模块管理员只配置关系，不自动取得全部业务查看权。
4. 学校地点通过正式 Excel 通道维护楼栋、教室和区域。业务模块只引用稳定地点标识；地点事实不得携带维修、卫生、内务或审批权限。

### 2.16 每个模块的九项冻结模板

每个模块在实施前必须填写两遍九项模板：

| 项 | 第一遍：业务冻结 | 第二遍：工程冻结 | 合格标准 |
|---|---|---|---|
| 1. 本阶段能力 | 用户/学校用白话列出本阶段真正要办的事 | 转为 operation、Reader、Handler 和状态边界 | 能说清现在能办什么，未完成能力不混入 |
| 2. 用户与身份 | 列出谁发起、谁查看、谁处理 | 映射服务端 actor_context 和任职来源 | 不接受前端或模型自报角色 |
| 3. 查询与正式动作 | 区分只读、草稿、需点击的正式动作 | 冻结动作名、风险级别、幂等和确认点 | 每个正式影响都能找到按钮和 Handler |
| 4. 权限事实 | 列出学校现实中的岗位、范围和关系依据 | 冻结模块二次鉴权六项及失败关闭 | 不把岗位名称当通用授权 |
| 5. 敏感字段 | 逐字段确认受众、能否入模型、保留和历史 | 冻结 direct/precomposed/compose、槽和 Reader 投影 | 未确认字段默认不进模型、不扩大受众 |
| 6. 呈现形态 | 说明文字、卡片或确认动作 | 冻结三档呈现、模板字段和 fallback | 模块结果不要求内核新增呈现类型 |
| 7. 初始化数据 | 列出学校需提供的主数据和模块配置 | 冻结 Excel/管理入口、source key、预检和审计 | 初始化不经过模型，不用显示名联表 |
| 8. 验收场景 | 用学校人员能复现的话列成功和失败 | 转成自动门、真实 PostgreSQL/身份门和用户手验 | 至少覆盖成功、缺项、取消、越权、重复和故障 |
| 9. 明确不做 | 用户写清本 checkpoint 不进入什么 | 转成源码/依赖/文档反膨胀门 | 不能用“以后再说”偷偷带入实现 |

第一遍由用户或学校业务责任人提供事实，Codex 只整理并指出矛盾；用户复阅冻结。第二遍由实现者把已确认事实翻译成契约和验收，用户再次确认没有语义漂移。不能只填字段名，不写现实主体、失败结果和明确不做。

### 2.17 点击办理模块

点击办理模块不是第一阶段交付前硬门，而是上线后按真实需要增加的补丁。学校初期若模型不可用，新自然语言不能办理或识别取消；系统诚实提示并回学校既有线下流程。已存在的历史、卡片、action_offer、正式结果和 recovery_control 在其他服务正常时仍可使用。

若学校实际使用证明需要点击兜底，再实现独立点击办理模块。它不要求每个业务模块另写一套表单，而是读取已启用模块的 OperationContractV1 双投影：

- model_projection：静态模型安全能力、候选字段名和含义形状，供第一次超级大脑；
- deterministic_form_projection：字段控件、必填/可空、选择器句柄、草稿入口和正式动作说明，供确定性表单。

点击路径为：

老师打开功能列表
→ 选择已启用模块和操作
→ 点击办理模块按 deterministic_form_projection 生成表单
→ 表单调用与对话路径同一模块草稿入口
→ 模块验证、二次鉴权并返回同一 ModuleResultV1/action_offer
→ 老师点击确认
→ 同一 Handler 幂等执行。

点击办理模块不复制业务规则、草稿、权限或 Handler。受控对象选择器仍遵守第 2.13 节的服务端裁剪、每页最多 20 项、choice_handle、选择后重验和零模型边界。

### 2.19 学校事实 Schema 与正式候选学校实例

学校事实层是第一阶段正式交付物，不是测试脚手架。实施顺序必须是：先完成业务中立的事实 Schema 和正式 Excel 通道，再生成模拟学校基础数据 Excel，通过完全相同的正式流程导入。

#### 学校事实 Schema

至少覆盖：

- 学校；`campus_locations(kind='campus')` 是唯一校区身份，不新建第二套校区主体表；同校组织与校区以有效期关系显式关联，覆盖全校的组织必须对每一个校区各有一条关系记录，绝不以“没有记录”代表全校。漏配因此只表示该组织不覆盖该校区，不会悄悄覆盖全校；
- 人员稳定标识、正式人事姓名与登录身份映射；正式人事姓名唯一权威是 `school_person_names`；`users.display_name` 只保存登录来源当前显示缓存（`legacy_login_label`），不得作为正式人事姓名，`login_mapping` 内容不保存该显示缓存，revision 18 不还原迁移前登录显示缓存历史；
- 组织层级；组织显式改挂仍沿用同一个稳定 ID 和 `source_key`，`parent` 变化形成独立 unit 与 lineage 并进入组织内容版本，历史 as-of 可还原当时上级；组织在任何时点均不得自指或形成环；
- 任职、作用组织、开始/结束时间、撤销状态和来源；任职与登录映射的每次内容变化形成新的明确内容切片，旧内容不被原地覆盖，未来生效切片在边界前不改变 current；任职计划到期日允许事后写入；
- 学生根、学生在校关系，以及学生在校关系中的主要就读校区和行政校区；
- 地点层级、类型、正式名称、别名、歧义和历史有效期；地点显式改变 `parent` 或 `kind` 后仍沿用原稳定 ID 和 `source_key`，结构变化进入地点内容版本并产生独立 unit 与 lineage，历史 as-of 可还原当时父链与类型；
- 宿舍房间属性、床位及版本、学生—床位有效期关系和学生在校关系中的走读/寄宿。学生—床位关系（Residence）只允许保存学生、床位、起止区间、撤销、版本和来源；不得保存事实之间的前后、转换或自关联字段；
- 联系方式、来源和可见范围；
- 制度资料、版本、分级、发布/生效/失效和替代关系，以及制度适用范围事实。每条适用范围记录的目标只能二选一：校区或组织，必须以“恰好一个”为约束；沿用 `official_contact_points` 的“组织或地点二选一 + CHECK 恰好一个”形状，不发明新形状；
- 导入批次、稳定 source key 和事实版本。

不得包含报修工单、维修责任组、请假审批链、卫生责任、内务整改或任何模块权限。事实层描述学校是什么，模块决定基于这些事实能做什么。

#### 权威优先级与版本语义

事实的有效区间表示现实事实；ChangeSet、unit 和 lineage 表示事实如何被正式改变；audit 表示谁在什么任职上下文执行；派生结构是非权威、可重建的，不得覆盖前三者。

根事实（学校、人员、学生根、组织、地点）的实体行 `version` 是当前实体的乐观版本。地点 `parent`／`kind` 与组织 `parent` 的历史内容以版本切片为 current/as-of 真值，稳定行只保留 latest-confirmed 兼容投影。非根事实的 canonical current/expected version 唯一取 lineage 的 `target_version`；非根事实物理行的 `version` 只表示创建该物理切片时的版本，不得作为并发输入或公共 current version。任职和登录映射的内容切片同样以 lineage `target_version` 标识，不把稳定投影版本当作内容版本。

#### 终止、撤销与历史读取

普通 upsert 不得清除或翻转终止/撤销状态。根身份类（学校、人员、学生根、组织、地点）重新启用必须使用显式 `reactivate`，沿用原稳定 ID，不得要求新的稳定来源身份；`reactivate` 不适用于任职或登录映射。切片/关系类（任职、登录映射）重新成立必须使用 `upsert` 形成新的明确事实切片，不得原地重开旧切片。

本阶段只有任职和制度版本具备“撤销但原到期日仍保留”的行级撤销语义：任职支持计划到期日，撤销不得覆盖它；制度版本撤销不得覆盖原 `effective_to`。在校关系、地点别名、宿舍房间、个人联系方式、学生联系人和公务联系方式不新增行级撤销标记，继续由有效区间与账本 operation 共同表达。将来若这六类升级为行级撤销标记，只有拥有完整 lineage 的数据可以机械回填；owner/legacy 的无 lineage 数据必须另行盘点，不能承诺一定可回填。

正式 Excel 导入通道中“文件删除一行不能暗示删除、撤权或结束，撤销和有效期必须显式表达”的原意不变；这不要求每张事实表都有行级撤销标记。撤销的权威记录是显式操作与账本。

只查询“当前有效事实”的读取可以按正式 current 语义读取事实行，不必查询账本。任何查询过去某一时刻状态的读取必须结合账本撤销语义；否则会返回从未成立过的事实。这是强制要求。

#### 旧任职直写入口

旧 `ConfirmStaffDutyBindingHandler` 把稳定任职和报修责任组成员作为一个旧式事务直接写入，不能产生任职内容切片、School Facts unit 和 lineage。该 Handler 的写入成功路径自 Checkpoint 3 起机械禁用；它没有生产路由，不得在 SF5 前作为兼容例外恢复。后续若仍需要这项能力，必须先重建为正式 Canonical 任职写入，再由报修模块按自己的边界处理责任关系；这项负债不改变或冻结任何报修业务语义。

#### 一校一库、多校区同库：DB-instance / school anchor 与 tenant RLS（冻结）

一个正式学校实例只绑定一个学校主体和一个独立业务数据库；同一学校的多个校区共用该数据库。请求、AI 和客户端不得选择目标学校；Excel 中的学校标识只用于绑定核对。每个正式学校数据库必须建立可机械验证的 DB-instance / school anchor，把数据库实例绑定到唯一学校身份；绑定错误、缺失或无法唯一验证时必须 fail closed。“一校一库”不得只作为文档约定，也不得成为撤销 tenant RLS 的理由。tenant RLS 继续保留，用于防御错库、错恢复、异常数据、错误配置和其他跨校异常。

本节只冻结安全目标，不冻结 anchor 的表名、字段名、fingerprint 编码、migration 内部结构、启动检查函数名、恢复命令或具体数据库对象；这些属于 SF5B 实现时在本边界内选择的工程细节。

#### 同校 Scope 的 R1 读取基线（冻结；SF5B 已按此实现并正式批准）

这里的 R1 是 SF5B Scope 方案编号，不是第 6 节业务风险等级。`campus_ai_runtime` 不获得敏感 School Facts 基表的通用 `SELECT`。同校业务行范围由 trusted actor、Thin Authorization、`ScopePlan` 与窄 Reader 共同执行；字段范围由 `Projection`、显式 SQL 列选择和专用 DTO 执行。

禁止 `SELECT *`、读取完整敏感 ORM entity 后再删字段、在授权/deny 判定之后才过滤，以及允许客户端提交任意 Scope、`WHERE` 或 field list。当前不建设通用 Scope-aware RLS，也不采用“签名 `ScopePlan` 数据库上下文 + 万能 Scope-aware RLS”的通用 R3。只有某个具体资源的 Scope 类型、层级、多目标规则、组合规则、生命周期和可索引 predicate 都已正式冻结后，才可逐资源评估升级为“Reader + ScopePlan + 资源级 Scope RLS”双重防御的 R2；不得为了实现 RLS 提前发明学校尚未批准的 Scope 产品语义。

#### School Facts 唯一 Writer 的隔离执行域（冻结；SF5B 已按此实现并正式批准）

对第 2.22 节“第一阶段不做执行域隔离”增加一个仅限 School Facts 正式唯一 Writer 的窄例外。现有 `contracts`、`SchoolFactChangeService` 与 `SqlAlchemySchoolFactPersistence` 组成的正式 Python 写入链继续是唯一业务语义 apply kernel；Writer Executor 只是该唯一写核的隔离宿主，不是第二写核。不得把 19 类 School Facts 的完整 apply 状态机复制到 PostgreSQL，也不得长期维护 Python 与 PostgreSQL 两套完整状态机。

内部受信 Writer Executor 与主系统同仓库、同制品、同版本发布，不拥有独立业务领域，不成为新业务模块、通用业务 API、面向其他模块的通用服务或独立业务微服务；它唯一的业务职责是执行正式 Python School Facts Writer。IPC、Unix socket、named pipe 或等价传输、进程启动、类型名、函数名和 wire format 属于工程自决。

Executor 必须处于独立容器和独立操作系统身份，或具有等价安全强度的执行隔离边界。API/runtime 与 importer API 均不得取得 Writer secret 或 DSN；Writer secret 必须独立注入，不得与 runtime/importer 共用可读环境、secret volume、凭据文件或等价权限。Executor 不持有 migration 或 DB-owner 凭据；runtime/importer 不得 `SET ROLE` 到 Writer，Writer 也不得 `SET ROLE` 到 migration/owner。Writer 数据库角色仍须最小权限，PUBLIC 不得取得 Writer 执行能力。

本方案不提供数据库层的 plan-exact 证明。数据库能够机械证明 runtime 和 importer 对 School Facts 基表零 DML、只有 Writer 执行域持有 Writer 数据库能力，并继续执行 CHECK、FK、RLS、CAS 与事务约束；但数据库不能证明 Writer role 发出的每条 SQL 都来自正常 Python Writer 控制流且精确属于批准 plan。因此安全模型是“进程级唯一业务写核 + 窄 TCB + 独立执行域 + Writer secret 隔离 + 数据库最小权限与约束”，不是数据库级 plan-exact Writer 证明。Writer Executor 或 Writer secret 被完全攻陷时，数据库无法排除 plan 外 SQL；这属于受信计算基或部署安全边界失陷，不得把“Writer role 已最小权限化”表述成数据库已证明所有写入 plan-exact。

Executor 只接受固定、类型化的正式写入协议，例如现有 prepare、confirm 与 result/receipt 查询族；确切 operation、函数名和 wire format 由实现决定。协议不得接受 SQL、任意表名、列名、`WHERE`、Python 代码、后台命令、数据库脚本或通用“执行某操作”入口。正式执行前必须在 Writer 边界重新验证 confirmation、plan hash、unit/hash 完整性、actor、session、authorization、版本/CAS 与 School Facts 当前状态；API 层验证不是最终 Writer 权威。

现有 batch、confirmation、idempotency、outcome 与 receipt 继续作为唯一业务终态权威。IPC、队列、socket 或 Executor 内部状态只能承载传输、lease、delivery 或 health；重复 confirm、调用方超时、Executor 崩溃和 commit outcome unknown 最终都必须回到持久 School Facts receipt/outcome 判断结果。whole-plan 仍由 Executor 中的一个 PostgreSQL transaction 完成。

`login_mapping` 对 Identity User 的存在、provider identity tuple 稳定性和必要锁定，可以通过 Identity 域自有的只读／窄锁 validator Protocol/Port 或等价 advisory-lock 协议提供给 School Facts Writer；具体 Port、SQL、锁与是否使用 identity-owned `SECURITY DEFINER` 属于工程自决。该协作不得修改 User Schema、identity 业务语义或认领/登录语义；School Facts 不得创建或修改 User，runtime/importer/Writer 均不得因此获得通用 `users UPDATE`，也不得形成第二个 Identity Writer。若实现需要突破任一边界，必须停止并请用户决定；仅在 Identity 所有权内增加上述窄协议不需要再次架构拍板。

上述决定不取消其他 SF5B 硬门：runtime School Facts DML 收口、importer 零事实基表 DML、runtime 敏感基表 `SELECT` 收口、role bootstrap allowlist 与 revision 20 权限收口一致且重建不得复活旧权限、tenant RLS、`Projection` 的 SQL pre-read hard gate、restricted 正文不得先读后 deny、旧 RBAC 不得与 Thin Authorization 做 OR/fallback、`platform/responsibility` 不得升级为 Governance Scope、SF5A 封存、revision 19 不修改、不提前挂 School Facts 产品查询，以及不进入 SF6/SF7。

至此 SF5B 三个阻塞架构分叉已关闭。以上段落保留当时的冻结结论；后续正式实现结果如下，不倒改冻结轮次的历史。

#### 正式 Excel 导入通道

模板、Schema 和导入器必须固定版本；所有引用使用稳定 source key，不用显示名联表。导入流程为：

上传
→ dry-run 全量预检
→ 输出 sheet/行/列和稳定错误码
→ 有权人员确认
→ 单事务写入
→ 记录导入批次和审计
→ 返回确定结果。

任一预检错误整批零写。同一文件重复导入必须幂等；文件中删除一行不能暗示删除、撤权或结束，撤销和有效期必须显式表达。初始化配置走确定性程序，不调用模型。

#### 模拟 Excel，正式运行

由项目方生成一份内容明显虚构、结构接近真实学校复杂度的基础数据 Excel，并通过上述正式通道导入正式候选学校实例。

模拟的是 Excel 内容；正式的是 Schema、导入器、数据库、RLS、身份解析、权限重验和业务运行路径。业务模块不得知道数据来自模拟 Excel 还是真实 Excel，不得存在模拟环境专属业务分支、跳过鉴权或特殊 Reader。

模拟 Excel 至少覆盖：

- 一人多岗；
- 跨组织兼职；
- 临时顶岗及独立有效期；
- 任职撤销但原计划到期日未到；
- 历史任职；
- 重名人员；
- 无联系方式和联系方式历史；
- 地点层级、别名、歧义、更名和失效；
- 制度版本撤销但原 `effective_to` 未到、分级、生效、失效和替代。

模拟 Excel 不含报修工单、维修责任组、审批链或其他业务偏见。业务模块自己的初始化数据在各模块接入时走该模块正式配置通道，并只引用学校事实稳定标识。

模拟数据使用明显虚构的人名、不可投递电话/邮箱和专用模拟登录身份；候选环境关闭短信、钉钉、企业微信和邮件真实外发，避免误通知真人。

#### 学校事实环境 checkpoint

任何业务模块接入前必须独立通过：

1. 同一 Excel 重复导入零变化；
2. 错误 Excel 预检后整批零写；
3. 重名只按稳定标识处理，不串人；
4. 一人多岗和兼职保持独立，不合并成单一角色；
5. 临时任职到期或撤销后新请求立即失效；
6. 受限制度正文不进入真实模型请求；
7. runtime 数据库角色不能直接修改主数据；
8. 客户端或模型自报 person、role、assignment、school 无效；
9. 真实 PostgreSQL、DB-school anchor、tenant RLS、身份解析和导入审计均走正式路径，错库或错恢复失败关闭。

#### 真实学校换表导入

学校正式接入时复用完全相同的 Excel 模板、事实 Schema、预检、确认、事务导入和运行代码，只替换为学校提供的真实内容。

真实数据必须导入一个干净的学校实例，不得在已经产生模拟工单、幂等记录和审计历史的候选数据库里原地替换。换的是学校实例和导入内容，不是通道、结构或模块代码。

开发单元测试可以使用隔离 fixture，但它只是开发资产，不进入产品设计、运行环境或学校验收证据。

### 2.20 风险批次与实现路线

模块按最敏感部分定级，不能因为包含一小段公开查询就提前放入低风险批次。

- 低风险候选：校历、学校地点。校历固定为学校事实 checkpoint 后第一个真实模块，用于建立干净的真实模块样板。
- 中风险候选：报修、通知、值班、场地预约、物资申领。报修在校历后进行内核化改造，用于验证多轮草稿、敏感槽、正式动作、RLS 和幂等；旧报修 checkpoint 只是内核前业务基线。
- 高风险候选：制度资料、通讯录、班级学生查询、请假、内务、卫生。
- 纪律最后，按最高影响单独设计和验收。

制度资料按受限正文部分定级，实际实施顺序在高风险档，不得以公开资料查询为理由提前上线。

最终实现路线写死为：

归属审计
→ 内核与无业务探针
→ 学校事实 Schema
→ 正式 Excel 预检与事务导入通道
→ 生成模拟学校基础数据 Excel
→ 通过正式通道导入正式候选学校实例
→ 学校事实环境 checkpoint
→ 校历首个真实模块
→ 报修内核化改造
→ 校历与报修两模块抗污染门
→ 其余模块逐个接入
→ 用户判断够用后进行真实学校换表导入与运行收口。

校历与报修两模块抗污染门必须证明：

- 超级大脑在两个模块之间选择正确，无法确定时澄清而非猜测；
- 两份静态能力说明不含运行期身份、权限或业务数据，也不互相污染；
- 校历接入后再接报修，内核零业务字段、零报修分支；
- 报修旧控制器、关键词分流、模型直连、旧确认和旧正式写入口退役，同一可见流和正式动作任一时刻只有一个权威。

每完成一个模块 checkpoint 必须停止，由用户决定继续下一个模块还是进入学校运行收口。

### 2.21 验收门

#### 内核门

- 无业务探针改名后，内核行为不变；
- 每句已接纳自然语言恰好一次第一次模型调用，无关键词捷径、无自动重试；
- 一回合最多一个模块，无 fan-out；
- direct、precomposed、compose 三档和第二模型 fallback 均通过；
- 字段句柄一致重命名后内核行为不变；
- 展示账本的敏感哨兵、卡片 DTO、direct 结果和填值文本在后续真实模型请求中为零；
- 多标签页 busy、不隐藏排队、停止三个阶段均迟到失效；
- 正式确认必须点击，模型和前端伪造 action_offer 无效；
- 刷新不重发、重启不复活未结算结果。

#### 学校事实环境门

以第 2.19 节 checkpoint 为准，必须使用真实 PostgreSQL、真实 runtime 角色、真实 RLS 上下文和正式导入通道；mock 不能替代。

#### 每模块门

- 九项模板两遍通过；
- 静态能力说明、MeaningV1 私有负载、ModuleResultV1 和敏感策略冻结；
- 当前身份、任职、学校、范围、责任和业务 revision 二次鉴权；
- 成功、缺项、澄清、取消、越权、重复提交、模型失败和模块失败均有证据；
- 真实 PostgreSQL 的正式动作、幂等和零越权写验证；
- 用户亲手验收通过并形成 checkpoint 后才挂入静态目录。

#### 学校运行收口门

- 用户明确当前已完成模块“够用”；
- 真实学校使用干净实例，通过同一 Excel 通道完成真实数据预检、确认和导入；
- 真实身份、权限、备份恢复、服务重启、模型健康、错误诊断和线下故障流程验证；
- 对学校只宣传已完成模块和真实边界；
- 半成品模块、模拟身份和候选数据不进入正式实例；
- 形成可回滚 checkpoint 后才可称“学校可直接用”。

### 2.22 第一阶段明确不做

- 不做摄像头、门禁或其他设备 API；
- 不做教学全屏、语音、触屏做题等教学功能；
- 不做多租户、多学校运营平台或微服务拆分；
- 不做跨模块一句话多任务编排、工作流引擎或多 Agent；
- 不做运行时模块注册中心；
- 不做跨对话长期记忆；
- 除第 2.19 节已冻结、仅限 School Facts 正式唯一 Writer 的隔离 Executor 窄例外外，不做其他执行域隔离、第三方恶意模块防护或公共合规工具链；
- 不做应用级资源配额/计费桶；宿主只保留不按应用区分的统一超时、请求大小和总内存硬上限；
- 不把上线后点击办理模块变成交付前硬门；
- 不为第二、第三阶段预留未使用字段、表、接口或呈现类型。

第二阶段：学校实际使用第一阶段后，设备能力通过设备模块和设备 API 适配层接入，内核不因设备业务改变。

第三阶段：学校实际使用第一阶段后，教学能力通过教学模块、语音转文字适配层和模块自己的呈现端接入，内核不因教学业务改变。

## 3. 技术形态与长期边界

- 前端：Vue 3 + TypeScript + Vite；
- 后端：Python 3.13 + FastAPI；
- 权威数据：PostgreSQL 16；
- 部署：单校模块化单体；第 2.19 节的 School Facts Writer Executor 是同仓、同制品、同版本的安全执行域窄例外，不是独立业务微服务；
- 模型：先使用可替换的云端超级大脑适配，模型和供应商不得进入业务事实；
- 文件：由需要文件的模块经受控存储能力接入；
- 正式写入：领域 Handler + UnitOfWork + 幂等 + 必要审计；
- 外部模型、消息和文件调用不得在持有业务数据库事务时执行。

任何后续变更若要求内核读取业务字段、用关键词理解老师说话、直接执行模型步骤、绕过点击确认、把系统敏感值送入模型，必须停止并回到设计层。内核自身的机械缺陷和安全漏洞可以修复；业务不适配只能修改业务模块或应用侧适配层。
