# 校园综合智能体平台总体设计






## 1. 目标与边界

本项目面向单所中学，服务教师、宿管、总务、值周老师、学校领导与系统管理员。平台以一个简洁的 AI 聊天入口为主，同时提供必要的角色工作台和系统管理后台。

平台不是只做制度问答，而是将三类能力统一在同一个入口中：

1. **知识问答**：依据学校已授权的制度、通知、课标和模板回答，并显示来源。
2. **实时数据查询**：查询设施、库存、检查与处理进度等结构化台账。
3. **业务上报与办理**：将自然语言或语音转换为反馈、检查、入库或待确认表单，再进入对应流程。

第一版不接入真实 OA、教务、门禁等外部系统；不处理学生成绩、心理档案和人事档案等高敏感数据；不让 AI 自行确认处分、扣分或审批。

## 2. 已确认的产品体验

### 2.1 统一入口

所有用户默认进入类似聊天助手的手机/电脑响应式界面：文字输入、语音转文字、附件上传、对话回答、资料引用和结果卡片。

教师或职工可直接输入：

- “病假怎么请？”
- “飞镖有几个？”
- “男生 1 栋 2 楼厕所好脏。”
- “302 空调怎么样？”

AI 依据意图、用户权限和可用数据选择知识库、业务模块或工作流处理。它不直接读写数据库，只调用经过权限校验的业务接口。

### 2.2 角色工作台与系统后台

普通教师以聊天、我的反馈、我的待办为主。具有业务职责的人员看到与自己相关的待办工作台；系统管理员维护账号、角色、地点、责任人、检查模板等基础配置。

| 角色 | 核心权限 |
|---|---|
| 普通教师、职工 | 问答、查询授权数据、上报反馈、查看本人进度 |
| 宿舍管理员 | 处理宿舍相关反馈、记录宿舍检查 |
| 总务人员 | 管理库存、设施、报修及后勤反馈 |
| 值周老师 | 核实检查与纪律上报 |
| 学校领导 | 确认处理决定、发布规则版本、查看统计 |
| 系统管理员 | 管理账号、角色、地点、责任人、模板与系统配置 |

## 3. 总体架构

```text
统一网页入口（文字、语音、附件）
        ↓
AI 编排层：意图识别、补充信息、工具选择、自然语言回复
        ↓
权限与审计层：身份、角色、数据范围、操作日志
        ↓
知识库 / 业务模块 / 外部系统连接器
        ↓
PostgreSQL + pgvector / 文件对象存储 / Redis 队列
```

采用**模块化单体**：业务代码处于一个后端项目中，但模块边界明确；未来通过连接器对接 OA、教务等系统。第一天不拆分为多个微服务。

## 4. 业务模块与复用关系

| 模块 | 管理内容 | 复用能力 |
|---|---|---|
| 知识库 | 制度、通知、模板、文档版本、RAG 引用 | 文件、权限、审计 |
| 校园设施 | 楼栋、地点、厕所、空调、设备状态 | 地点、照片、反馈、工单 |
| 检查管理中心 | 卫生、宿舍、食堂、校园环境检查；整改与复查 | 模板、评分、照片、流程、统计 |
| 宿舍管理 | 楼栋、宿舍、住宿学生、宿舍专属检查 | 检查管理中心、地点、权限 |
| 纪律管理 | 事件上报、核实、规则匹配、处理与计分 | 工作流、规则中心、审计 |
| 后勤总务 | 物资入出库、库存、报修、环境反馈 | 地点、附件、通知、流程 |
| 食堂管理 | 菜谱、卫生检查、留样、反馈 | 检查管理中心、地点、附件 |
| 教学模块（后期） | 课表、场地、教学资料 | 身份、权限、外部连接器 |

“宿舍卫生检查”“教室卫生检查”“食堂卫生检查”共享同一个检查引擎，区别只在检查模板、对象字段和规则。不能为每一种地点重复开发一套审批、整改、复查和统计代码。

## 5. 关键业务规则

### 5.1 反馈、报修与检查

- 明确描述卫生、环境或服务问题且信息足够时，系统直接生成“待处理反馈”，并按地点责任规则分派；用户可在“我的反馈”查看进度。
- 反馈不等同于报修。工作人员核实后，可将反馈转为整改任务、巡查任务或报修工单。
- 信息不足时，AI 只追问必要信息，例如“男生公共厕所好脏”需要补充楼栋和楼层。
- 反馈状态由反馈领域拥有；地点未配置责任人时，业务记录正常保存并创建由明确业务任职承接
  的独立受限派单任务，不把技术管理员或派单任务状态塞进反馈主状态。

### 5.2 库存与设施查询

- “飞镖有几个？”按数量语义优先查询库存；若有库存记录，返回当前库存、地点和更新时间。
- “飞镖”单独出现时可能是人名或物资名，系统必须要求选择人员或物资，不能猜测或泄露人员信息。
- 设施状态以设施台账、检查记录和维修工单为准。没有记录时明确说明无法判断；“最新维修记录显示正常”不等同于实时状态正常。

### 5.3 学生纪律与规则

- 普通教师、宿管只能上报纪律事件；值周老师和学校领导才能核实或确认。
- AI 只能提取事实、补充时间地点证据、匹配候选规则和生成待确认材料；不得自动认定违纪、扣分或通知相关人员。
- 流程为：`上报 → 待核实 → 值周老师核实 → 领导确认 → 计分/处理 → 通知/归档`，驳回和补充材料均保留日志。
- 学校纸质制度是权威来源。系统保存扫描件和可执行规则草稿；规则须经领导审核发布为带生效日期的版本。每条事件绑定当时生效的规则版本，旧记录不可因新规则而被重算。
- 固定分值可在确认后自动计算；区间分值或严重事项仅给出建议，最终由有权限的人员决定。

## 6. 照片、文件与语音

- 检查照片、报修照片和附件存入校内对象存储（生产环境使用 MinIO 或校内 NAS）；PostgreSQL 仅保存文件地址、关联业务记录、上传人、时间、哈希和访问权限。
- 图片不使用公开链接；上传时限制格式和大小，生成缩略图并移除不必要的 EXIF 信息。
- 学生纪律照片采用更严格的访问范围和保留策略。
- 语音输入使用云端普通话语音识别。音频仅用于即时转写，转写后回填输入框，用户可修改并手动发送；不长期保存原始音频。第一版不做语音播报。

## 7. 目录边界

```text
apps/api/app/
├─ core/                 # 配置、鉴权、日志、限流
├─ db/                   # 数据库与迁移基础设施
├─ platform/             # identity、agent、files、rules、workflows、notifications、audit
├─ domains/              # knowledge、campus、inspections、dormitory、discipline、logistics、cafeteria
└─ integrations/         # llm、speech、oa（后期）、academic_system（后期）

apps/web/src/
├─ features/             # chat、knowledge、inspections、dormitory、discipline、logistics、cafeteria、admin
├─ shared/               # 通用表单、表格、照片上传、权限组件
├─ api/ router/ stores/ styles/

docs/                    # 架构、规则、接口、运维、决策记录
infra/                   # Docker、Nginx、Redis、MinIO、监控
scripts/                 # 启动、初始化、备份、导入脚本
runtime/                 # 仅本地临时数据，永不提交 Git
```

不创建“厕所模块”“扫把模块”等按单一物品命名的代码。新业务应先判断能否复用既有领域：设施、库存、检查、反馈、规则或流程。

## 8. 分阶段交付

整个校园平台不可一次性开发。优先采用纵向小闭环：

1. **V0：统一入口与通用反馈**：登录、角色、地点责任人、卫生/环境反馈、处理进度、照片、审计。
2. **V1：学校资料与检查**：知识库问答、文档引用、通用卫生检查、整改与复查、宿舍检查模板。
3. **V2：总务与纪律**：库存、设施、报修；纪律上报、核实、规则版本与处理流程。
4. **V3：食堂与教学扩展**：食堂台账与检查；按授权接入课表等教学数据。
5. **V4：外部系统集成**：OA/教务 API、状态同步、失败重试、审计与权限映射。

每个阶段只在前一阶段真实运行后再启动。禁止一次生成全部模块；AI 编码须以本设计、模块接口和当前任务所需文件为上下文，避免架构漂移。

## 9. 开发与验证原则

- 先写清状态表、权限表、输入输出示例和异常边界，再写代码。
- AI 生成代码只在单个明确模块内进行；平台能力通过稳定接口复用，不允许业务模块绕过权限层直接访问其他模块的数据表。
- 真实云端语音、模型 API、照片存储和手机浏览器必须在开发/试运行环境中逐步联调；代码生成不等于生产可用。
- 每一项高影响写操作（库存、纪律、扣分、审批）必须经授权人员确认；普通反馈可直接创建待处理记录。
- 文档、照片、规则和业务数据都需要备份、访问控制和操作留痕。
